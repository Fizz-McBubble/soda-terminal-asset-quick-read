# Independent Asset Quick Read installer

Version fields name different artifacts: this source prepares candidate setup 1.1.5 containing the unchanged Bridge 1.0.10 payload from published setup 1.1.4. The website's `src/assetQuickRead/releaseManifest.json` pins an exact package size, SHA256 and component mapping; a source edit does not publish or install that package. Current publication and machine installation must be checked independently. The installer recognizes the exact published 1.1.4 and 1.1.3 catalogs, uninstaller and Bridge identity, as well as older pinned versions. The full archive and each selected protocol file must match their fixed sizes and SHA256; three parallel requests share one verified archive. No protocol JSON is embedded in the public installer. Pass `-RuntimeDirectory <reviewed-runtime>` to `Build-AssetQuickReadInstaller.ps1` when rebuilding. This directory must match the Bridge's fixed native SHA256, approved drivers and fixed protocol hashes. Build and self-tests do not perform a real user installation or capture. Set `SODA_ASSET_QUICK_READ_PREVIOUS_PACKAGE` to a reviewed published 1.1.3, 1.1.2, 1.1.1, 1.1.0 or 1.0.10 package during self-tests to validate complete payload upgrade and registration-failure rollback in an isolated root with in-memory registration stores; it never writes HKCU.

The candidate output is a Windows x64 .NET 8 self-contained installer: `SodaTerminal-AssetReader-Setup-1.1.5.exe`. The candidate retains the pinned NSIS 3.13 compression wrapper around the branded installer and reviewed runtime payload. A release build needs no separately installed .NET runtime or NSIS; its complete runtime and wrapper license notices are retained.

```powershell
./Build-Bridge.ps1 -DotNetPath <dotnet.exe> -OutputDirectory <new-build-directory> -RunTests
./Build-AssetQuickReadInstaller.ps1 -DotNetPath <dotnet.exe> -BridgeOutputDirectory <new-build-directory> -OutputDirectory <new-installer-directory> -RunTests
```

Build uses the .NET 8 SDK, win-x64 runtime/reference packages at 8.0.29; standard NuGet sources are used when dependencies are not already cached. All output directories must be new. Optional `-NsisPath <makensis.exe>` checks the exact compiler hash in `installer/nsis-toolchain.json`. No build or self-test writes HKCU, requests UAC, captures traffic, loads a driver or reads a player's game files. Self-tests substitute local fixture protocol streams; they never download protocol data.

Only clicking **开始安装 / 升级安装 / 修复安装** authorizes the candidate installer to create `%LOCALAPPDATA%/SodaTerminal/AssetQuickRead/versions/1.1.5`, register the current-user protocol and add `Soda Terminal 资产快读` to the Start menu. The installer displays the tool name, installation version, and the recognized existing version. Installation details explain this boundary; the compact branded window keeps progress, success and retry messages free of internal error codes. The complete .NET/runtime/WinDivert file payload is embedded. The three protocol JSON files are deliberately absent from the embedded payload because their distribution permission is separate from the upstream MIT code license. Installation downloads exactly these public files from the fixed upstream commit, with no cookies, credentials or redirects:

- `https://raw.githubusercontent.com/pingwinekZ/zzz_packet_capture_0delay/4853f07c8fb5322c12b9b580d6364b577c2ac96a/assets/datamine.json`
- `https://raw.githubusercontent.com/pingwinekZ/zzz_packet_capture_0delay/4853f07c8fb5322c12b9b580d6364b577c2ac96a/assets/nap.json`

The installer shows byte-based copy/download progress and supports cancellation, errors and retry. Every downloaded file must match the fixed protocol size and SHA-256. No completed version or protocol registration is created on a failed/cancelled download. A verified identical version can be reopened without replacing its files. Repair of a missing or damaged same-version payload first builds and verifies a complete replacement. It then moves the complete original directory to `versions/.repair-1.1.4-<unique-id>` before promoting the replacement and registering it. The backup retains modified files, unknown files and empty directories and is outside automatic version retention. Failed registration or cancellation restores the original directory and registration; a replacement changed by another writer is preserved in this operation's `.install-<unique-id>` directory. No original directory is recursively deleted. Links and unexpected version-path files are rejected. Busy directories stay intact; finish/cancel reads and exit the confirmed tool, or save work and restart Windows before retrying. Jobs, outputs, other versions and uninstall history are preserved by repair. Existing foreign protocol or Start-menu registrations are rejected rather than overwritten.

The published 1.0.0 registration can upgrade to 1.0.1 only when its complete protocol shape and exact quoted command point to `versions/1.0.0/Soda.AssetQuickRead.Bridge.exe` under the same installation root, and the old executable, assembly, dependency/runtime configuration and Rust native core match the five fixed identities from the published installer. Different roots, command arguments, registry additions and replaced old binaries remain conflicts. An upgrade changes only the protocol command; existing versions and jobs remain. A later failure restores the previous command only while the new command still matches this transaction, preserving any subsequent unknown external change.

The current candidate also includes a separate self-contained uninstaller (embedded by default, or SHA-256 pinned inside the NSIS archive), adds an owned Windows Installed Apps entry, and offers uninstall from the installer when an existing tool is detected. Its file and entry are created in the same installation transaction; registration failure restores the old protocol and removes only newly created owned files. Uninstall removes exact matching program files from the current catalog and the fixed published 1.0.0 catalog, the exact owned protocol/Start-menu URL, and its matching uninstall program/entry. Modified files, unknown registry values, jobs and all account data remain. A locked program produces a retryable failure. The installed uninstaller relocates to a unique temporary directory before removing its own installed EXE; build tests do not run it against the real user root. That temporary executable is retained after process exit for subsequent normal temporary-file cleanup, rather than scheduling a broad delete command.

Self-tests use an in-memory protocol store and an isolated shortcut path, never the real registry or Start menu. `SODA_ASSET_QUICK_READ_LEGACY_FIXTURE` may point to a reviewed local published 1.0.0 package for actual five-file hash verification within synthetic roots; otherwise the same upgrade and rollback cases use a digest double. `SODA_ASSET_QUICK_READ_PACKAGE_FIXTURE` may point to an existing setup directory to reuse its already verified payload in synthetic tests. Both overrides are consulted only by `--self-test`, not normal installation.

The registered command is `"<installed bridge exe>" --protocol "%1"`. Only the exact `soda-asset-quick-read://launch` and its single trailing-slash form are accepted. Queries, fragments, arguments, targets, encoded paths and arbitrary URLs are rejected. Protocol and Start-menu launch try `127.0.0.1:50609`, then the fixed `46009` and `46010` candidates after an actual bind failure; they do not request UAC or change HTTP.sys URLACL/firewall settings. Duplicate opening verifies a current-user named pipe's OS process owner, the executable and assembly hashes, and health identity before exiting successfully. Unknown/different-build services or occupied ports fail without stopping another process. Installer startup uses fixed process exit codes: 74 only when every candidate address is occupied, 75 only when Windows denies every candidate, and 76 when an existing instance cannot provide a trusted identity within its bounded wait. Mixed failures and legacy exit 73 retain the combined unknown classification. Each provides retry/restart/feedback steps without terminating unknown processes or disabling protection. Exit codes never grant service ownership, and persistent service stderr is not redirected through the installer. The named pipe contains only a public version marker, never tokens or account data.

Upgrade discovers a pinned published service on every fixed candidate port. Readiness and service removal require the loopback TCP listener's OS PID to match the identity pipe's OS PID as well as the pinned executable/assembly, version and health record. A different process copying the public health fields grants no authority. Switching still requires the installer's explicit confirmation. Uninstall validates registration and file ownership first, then rechecks and stops only a verified owned connection service before the existing all-file busy preflight. The current version uses the embedded catalog's executable/assembly pins; older versions use the fixed published pins. Unknown processes remain running, and busy-file/stop-race failures preserve files and entries before removal starts. Users must finish or cancel reads first; elevated capture children are not terminated by this service stop. Uninstall failures use the finite `uninstall` diagnostic stage and safe feedback codes, without displaying raw exception paths.

`--service-recovery-self-test <report.json> <published-1.1.1-package> <published-1.1.2-package> <bridge-build-directory>` verifies actual old payloads and starts only health-only fixture processes on random non-production ports/private pipes in a new synthetic root. It covers fallback discovery, a foreign listener mirroring public health, process/start-time races, the actual loaded `clrjit.dll` lock, confirmed switching and current/old service uninstall recovery with in-memory registration stores. `SODA_SERVICE_RECOVERY_REUSE_ROOT` may reuse an unchanged fixture created by this same evidence directory; its identity and files are rechecked, and changed fixtures are rejected.

`GET /health` for the candidate 1.1.4 setup reports `service=soda-asset-quick-read`, Bridge `version=1.0.10`, `protocolVersion=1`. Actual capture retains the bridge's original exact Origin, Host, RAM-token, explicit `riskAcknowledged`, game-closed preflight, fixed runtime/driver/protocol hash, ready-based 180-second timer and cancellation/late-result protection. Only authenticated `POST /jobs` can request UAC. Installing or opening is not capture acceptance.

The payload includes upstream MIT, complete WinDivert LGPLv3/GPLv3/GPLv2, .NET runtime license and third-party notices. The matching official WinDivert 2.2.2 corresponding-source ZIP is supplied alongside the release installer; it is not installed into the user's runtime directory. Source and application-code rebuilding are documented by the standalone public repository. Real user installation, protocol registration, UAC/driver/game capture and user acceptance require their own evidence; build/self-tests do not perform them.

`installer/Rust-DEPENDENCY-NOTICES.txt` contains the complete license/copyright/NOTICE documents from all 70 locked registry dependencies and five upstream path crates, including combined-license dependencies such as ring/BoringSSL and Unicode. `Rust-STDLIB-COPYRIGHT.html` preserves the pinned Rust 1.97.1 standard-library copyright and license notice in full. Both files are included under the installed `licenses/` directory. `Build-RustDependencyNotices.ps1 -OutputDirectory <new-directory> -CargoPath <cargo.exe> -RustcPath <rustc.exe>` regenerates these solely from locked offline Cargo metadata and checksum-verified cached `.crate` archives; it never prints machine-specific metadata paths. It includes Apache NOTICE files whenever present, fails if a complete license document/archive is missing, and records the Cargo.lock hash. Installation packaging rejects stale/missing notices. The WindowsDesktop 8.0.29 runtime nupkg contains a complete `LICENSE` and no separate third-party-notices document; packaging also checks all runtime nupkg entries for any additional notices instead of relying only on extracted cache filenames.

The reviewed NSIS wrapper starts the same branded installer UI before expanding its fixed payload and uninstaller. Its size/SHA catalog validates the extracted uninstaller before installation; extraction errors signal failure and the wrapper waits for the child and propagates its exit code. This packaging requires no shared or newly installed system runtime. Offline tests drive actual UI buttons into the production filesystem installation/uninstall engines; process dispatch observers check the exact installed Bridge and browser URL without starting services or a browser.

The three pinned JSON files are first reused from reviewed installed versions only after exact size and SHA256 verification. Missing files download with at most three concurrent operations. Each tries the fixed GitHub raw and contents sources in two bounded rounds, then a shared official codeload archive from the same fixed commit with at most two attempts. Headers and idle reads each have a 30-second budget; each attempt has a five-minute limit. The archive must match 556,844 bytes and SHA256 39EB5B5C3D2AC9E5F207280902112FF0DE08B38966FDD49B25D7BCB92F8EB640; only the exact three entries are read in memory and checked against individual pins. No arbitrary mirror, disk extraction or bundled protocol JSON is introduced. Candidate Bridge health and assembly metadata are version 1.0.10.

Installer diagnostics are retained in %LOCALAPPDATA%/SodaTerminal/AssetQuickRead/installer-diagnostics/latest.json. They contain only version, finite phase/error/source codes, item index and elapsed milliseconds, never raw exceptions, paths, URLs, credentials or account data. Local permissions and registration failures no longer receive a generic network instruction. The 1.0.2 installer did not persist this record, so an earlier failure cannot be retrospectively attributed to a particular network error.

Release version checks use "--published-service-recovery-self-test <report.json> <published-1.1.3-package> <bridge-build-directory>" for the exact released 1.1.3 catalog, stub and actual isolated Bridge 1.0.9 process. It verifies confirmed switching to the current candidate, stale process rejection, owned-service removal before loaded runtime deletion and preservation of modified/unknown files and results. The broader 1.1.1/1.1.2 recovery counterexamples remain a separate reusable suite.

The 1.1.5 candidate checks DELETE access before uninstalling, reusing the existing guarded removal primitive. A delete-shared reader is permitted even if it denies writes; a reader denying deletion still blocks before components or registration are removed. It does not stop or remove a shared WinDivert driver service. Run `--uninstall-self-test <report.json>` for the isolated removal suite without rerunning unrelated installer tests. Native builds, this test, and the public website remain separate from actual-machine acceptance.
